# datadog-api-client-go split packages

This branch contains the autogenerated Go client packages for the [Datadog API](https://docs.datadoghq.com/api/). Instead of one module with every API, the client is split into a core module and one module per product area, so you depend only on the APIs you use. The code is generated from Datadog's public OpenAPI specifications by internal tooling.

The single-module client, `github.com/DataDog/datadog-api-client-go/v2`, lives on the `master` branch and is released separately. The two can be used side by side.

## Requirements

- Go 1.22+

## Layout

Every directory under [`packages/`](packages) is its own Go module:

| Directory            | Module                                                        | Contents                                                                                                                                                      |
| -------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/core`      | `github.com/DataDog/datadog-api-client-go/packages/core`      | Configuration, authentication, HTTP, retries, compression, servers, errors, pagination and serialization (`api/datadog`), and AWS authentication (`auth/aws`) |
| `packages/<package>` | `github.com/DataDog/datadog-api-client-go/packages/<package>` | The APIs of one product area, in the `datadogV1` and `datadogV2` namespaces                                                                                   |

For example, `packages/monitors` holds `MonitorsApi` and `DowntimesApi`, imported as `github.com/DataDog/datadog-api-client-go/packages/monitors/datadogV1` and `.../packages/monitors/datadogV2`. Each package's README describes its APIs; see `packages/` for the full list.

## Installation

Add the core together with the packages you use:

```sh
go get github.com/DataDog/datadog-api-client-go/packages/core github.com/DataDog/datadog-api-client-go/packages/monitors
```

## Getting Started

Here's an example listing monitors:

```go
package main

import (
    "context"
    "fmt"
    "os"

    "github.com/DataDog/datadog-api-client-go/packages/core/api/datadog"
    "github.com/DataDog/datadog-api-client-go/packages/monitors/datadogV1"
)

func main() {
    ctx := datadog.NewDefaultContext(context.Background())
    configuration := datadog.NewConfiguration()
    apiClient := datadog.NewAPIClient(configuration)
    monitorsApi := datadogV1.NewMonitorsApi(apiClient)

    resp, r, err := monitorsApi.ListMonitors(ctx)
    if err != nil {
        fmt.Fprintf(os.Stderr, "Error when calling `MonitorsApi.ListMonitors`: %v\n", err)
        fmt.Fprintf(os.Stderr, "Full HTTP response: %v\n", r)
    }
    fmt.Fprintf(os.Stdout, "Monitors: %d\n", len(resp))
}
```

Save it to `example.go`. Set `DD_API_KEY` and `DD_APP_KEY` to your Datadog credentials, and `DD_SITE` if you don't use `datadoghq.com`, then run `go run example.go`.

The core's README covers authentication, servers, unstable operations, retries, proxies and the JSON encoder.

## Migrating from `github.com/DataDog/datadog-api-client-go/v2`

The types, constructors and methods are the same as the monolith's. What changes:

- **Import paths.** `.../v2/api/datadog` becomes `.../packages/core/api/datadog`, and `.../v2/api/datadogV1` or `.../v2/api/datadogV2` becomes the namespace of the package that holds the API, such as `.../packages/monitors/datadogV2`.
- **Moved operations.** 71 operations belong to a different API class in their package than in the monolith, such as `SecurityMonitoringApi.ListFindings`, which is `SecurityFindingsApi.ListFindings` in `security-findings`. [`package-mapping.json`](package-mapping.json) lists every operation with its monolith name (`v2.SecurityMonitoringApi.ListFindings`), its package, namespace, class and method.
- **Context keys.** The core's context keys, such as `datadog.ContextAPIKeys` and `datadog.ContextServerVariables`, are different values from the monolith's. A context built with the monolith's `datadog.NewDefaultContext` carries no credentials for calls through the packages, so build it with the core's `datadog.NewDefaultContext`.
- **Import aliases.** Every package names its namespaces `datadogV1` and `datadogV2`, so a file that uses two packages, or a package and the monolith, needs aliases:

  ```go
  import (
      ddcore "github.com/DataDog/datadog-api-client-go/packages/core/api/datadog"
      monitorsv2 "github.com/DataDog/datadog-api-client-go/packages/monitors/datadogV2"
      findingsv2 "github.com/DataDog/datadog-api-client-go/packages/security-findings/datadogV2"
  )
  ```

- **Unstable operations.** The keys are unchanged, `v2.<OperationId>`, such as `configuration.SetUnstableOperationEnabled("v2.ListFindings", true)`. The core records any key, so a mistyped key isn't reported until the call fails with `Unstable operation 'v2.<OperationId>' is disabled`.
- **Operation servers.** `configuration.OperationServers` keys keep the monolith's class, `"<APIVersion>.<ApiName>.<OperationName>"`, also for moved operations.

## User-Agent

Each request sends `datadog-api-client-go/<package>/<package version>` followed by `configuration.UserAgent`, which defaults to `core/<core version> (go <version>; os <os>; arch <arch>)`. Replacing `UserAgent` keeps the package token.

## Versioning

Each module is versioned on its own, with its version in its `version.go`. From major version 2, a module's path ends in `/vN`, such as `github.com/DataDog/datadog-api-client-go/packages/monitors/v2`. Every package requires the core version it was generated with; `go get` the core with the packages you use.

## Tests

[`tests/`](tests) is a separate module that runs the BDD scenarios of `tests/scenarios/features` against the split packages, through `replace` directives to `packages/`. Generation writes the features and the `tests/scenarios/generated-test` data, and the `go_split_package` generator writes `tests/scenarios/package_mappings.go`, which imports every package namespace and names the package class of each moved operation. The other runner files are kept by hand, as copies of `master`'s, and pre-commit runs `scripts/tidy-tests.sh` to keep `tests/go.mod` in line with `packages/`.

The scenarios replay recordings through the generated test server, which needs `python3`; there are no Go cassettes on this branch:

```sh
cd tests
DD_USE_GENERATED_TESTS=true go test ./scenarios -count=1
```

Set `BDD_TAGS` to a comma-separated list of tags, such as `BDD_TAGS='@endpoint(monitors)'`, to run only some scenarios.

## Contributing

The code on this branch is generated: don't edit it by hand. Changes to the APIs come from Datadog's OpenAPI specifications, and generated pull requests are opened against this branch by internal tooling. Changes to the branch's tooling (pre-commit hooks, CI and the scripts under `scripts/`) are welcome as pull requests.
